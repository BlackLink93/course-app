# ЛР 1. Старт проекта на React и TypeScript

Создан каркас приложения «Каталог фильмов и сериалов» на React + TypeScript + Vite.
Начальный экран содержит название, описание и пустой раздел списка записей.

## Шаги проверки

1. `npm ci` в папке frontend — зависимости устанавливаются без ошибок.
2. `npm run dev` — сервер запускается, экран открывается на localhost:5173.
3. Ошибок в терминале и в консоли браузера нет.
4. Текст читается на узком экране без горизонтальной прокрутки.
5. `npm run build` — проверка типов и сборка проходят успешно.
6. `npm run preview` — готовая сборка открывается и отображает экран.

# ЛР 4. Загрузка справочника по HTTP

через fetch из `frontend/public/demo/genres.json`. Добавлены тип

хранится как id справочника. Страница записи показывает название жанра

## Шаги проверки

1. Network, фильтр genres.json: при открытии формы виден GET со статусом 200,
   в Response массив жанров. Запись с выбранным жанром создаётся,
   при редактировании выбран тот же жанр.
2. Slow 4G: во время загрузки видно «Загружаем жанры…», кнопка
   «Сохранить» недоступна, остальные поля и «Отмена» работают.
3. Offline перед открытием формы: появляется ошибка. Ввести название,
   вернуть Online, нажать «Повторить» — название сохранилось.
4. Временно неверный путь в `genresUrl`: появляется ошибка загрузки

5. `[]` в genres.json: отдельное сообщение «Жанров пока нет», сохранение

7. Slow 4G: открыть форму и сразу уйти к списку — список не меняется,
   ошибка не появляется.
8. Жанр удалён из JSON: при редактировании видно «Текущий код: …»

# ЛР 5. Схема данных и справочник в Supabase

Справочник жанров перенесён из `public/demo/genres.json` в таблицу Supabase
`public.genres`. Форма читает его через общий клиент `src/lib/supabase.ts`
и сервис `src/services/genres.ts`. Состояния загрузки, ошибки, пустого
справочника и повтора из ЛР 4 сохранены, добавлена кнопка «Обновить справочник».
Основные записи пока остаются в состоянии App и после перезагрузки возвращаются
к демонстрационному набору. JSON ЛР 4 перенесён в `docs/examples/genres.json`
как пример и приложением больше не используется.

## Схема

| Таблица | Назначение | Ключ | Связь | Доступ |
| --- | --- | --- | --- | --- |
| `genres` | Справочник жанров: `id`, `name` | `id text` | — | Публичный: anon и authenticated только читают |
| `media_entries` | Фильмы и сериалы пользователя | `id uuid` | `owner_id` → `auth.users.id`, `genre_id` → `genres.id` | Личный: в ЛР 5 закрыт от клиентских ролей |

Ограничения `media_entries`: название от 3 до 100 символов без учёта пробелов
по краям, описание не длиннее 500 символов, `kind` — `movie` или `series`,
`status` — `planned`, `watching` или `watched`, год выхода от 1888 до 2100,
оценка от 1 до 10. Поле `genre` во frontend соответствует `genre_id` в БД,
поле `year` — `release_year`.

## Порядок применения

1. В SQL Editor целиком выполнить `supabase/migrations/202611082300_initial_schema.sql`.
2. Затем целиком выполнить `supabase/seed.sql`.
3. Создать `frontend/.env.local` по образцу `frontend/.env.example`
   и перезапустить `npm run dev`.

# ЛР 6. Авторизация и сохранение личных записей

Добавлены регистрация и вход по email и паролю (`src/pages/AuthPage.tsx`),
состояние сессии (`src/hooks/useAuth.ts`), защита личных маршрутов
(`src/app/RequireAuth.tsx`) и выход в шапке. Записи хранятся в таблице
`media_entries` Supabase: сервис `src/services/media.ts` читает, создаёт,
изменяет и удаляет их и переводит столбцы БД в поля интерфейса. Записи
сохраняются после перезагрузки и повторного входа. Демонстрационные записи
`src/data/media.ts` больше не импортируются и не смешиваются с личными.
Предупреждение о временном хранении убрано из шапки.

## Настройки Auth

- Вход по email и паролю: <заполнить: включён>.
- Подтверждение email: <заполнить: включено / выключено>.
- Site URL и Redirect URLs: <заполнить, например http://localhost:5173>.

Пароли проверочных аккаунтов в репозиторий не записываются.

## Маршруты

- `/auth` — вход и регистрация, публичный. Вошедший пользователь
  перенаправляется к списку.
- `/media`, `/media/new`, `/media/:id`, `/media/:id/edit` — только после входа.
  Гость перенаправляется на `/auth`, пока сессия проверяется, показывается
  «Проверяем сессию…».
- Неизвестный адрес — страница «не найдено».

## Модель доступа

- `genres` читают все (anon и authenticated), изменять из браузера нельзя.
- `media_entries` читает, создаёт, изменяет и удаляет только владелец:
  отдельные политики SELECT, INSERT, UPDATE и DELETE с условием
  `auth.uid() = owner_id`. anon не имеет прав на таблицу.
- `owner_id` новой записи задаёт база через `default auth.uid()`,
  клиент его не передаёт.

## Порядок применения

1. Миграция ЛР 5 и seed уже применены.
2. В SQL Editor целиком выполнить
   `supabase/migrations/202611082310_media_entries_owner_policies.sql`.
3. В Authentication → URL Configuration добавить адрес Vite в Redirect URLs.

Фактическая дата применения в учебном проекте: <заполнить>.

## Сценарий двух аккаунтов

1. Войти как A, создать две записи, обновить страницу, изменить одну.
   Записать id одной строки.
2. Выйти: список очищен, `/media/<id>` перенаправляет на `/auth`.
   Войти снова как A — изменения на месте.
3. Войти как B: записей A не видно. Создать запись B, обновить страницу.
4. Временный `select` из `media_entries` с `owner_id` пользователя A
   под сессией B: строк A нет.
5. Временные `update` и `delete` по id записи A под сессией B:
   запись A не изменилась (затронуто ноль строк).
6. Временный `insert` с `owner_id` пользователя A под сессией B:
   отклонён политикой WITH CHECK. Проверочный код удалён.
7. Вернуться к A: записи A не изменены, запись B не видна.
8. Создание, редактирование, отмена, удаление, фильтр и справочник работают.

## Проверки ошибок

1. Неправильный пароль: ошибка, email сохранён.
2. Регистрация при включённом подтверждении: сообщение «Проверьте почту…»,
   сессии нет, личные страницы недоступны.
3. Личный адрес без входа и во время проверки сессии: данных не видно.
4. Сеть выключена при загрузке списка и сохранении: ошибка видна,
   черновик формы сохранён, после восстановления сети «Повторить» и повторное
   сохранение работают.
5. Двойное нажатие «Сохранить»: второй запрос не отправляется
   (кнопка заблокирована до ответа).
6. Выход: список очищается сразу.
7. `npm run build` и `npm run preview` проходят.
